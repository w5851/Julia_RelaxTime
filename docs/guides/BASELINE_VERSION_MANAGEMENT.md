# Baseline Version Management Guide

内部基线是有版本的数值契约。用于保护既定行为；与文献或独立实现的比较属于 validation，正式生产遵循专题 SOP。测试分类以[测试治理](../dev/testing_governance.md)为准。

## 何时修改

| 变化 | 处理 |
| --- | --- |
| 新的代表点、观测量或数值承诺 | 生成独立候选，审查后引入新版本 |
| 物理/数值 bug 修复 | 先检查旧基线，明确预期差异；修复动作本身不自动授权更新 |
| 无语义的重构、性能优化、文档变化 | 保留现有基线，运行受影响检查 |
| 读取器、格式或索引变化 | 用现有数据和夹具检查兼容性；除非数值定义改变，否则不重算 |
| 断言容差调整 | 说明误差来源与证据；不因调整容差重生 CSV |

普通回归失败先诊断代码、输入和环境。未解释的漂移不能通过刷新基线或放宽容差解决；旧基线包含已知错误时允许相关检查失败，但须解释，不要求先让全仓旧基线变绿。

## 数据与来源

- 内部基线通常位于 `tests/baselines/<domain>/baseline_<feature>_<scope>_vN.csv`，消费者位于 `tests/regression/<domain>/`。沿用该主题现有命名，避免只为统一文件名迁移历史数据。
- CSV 保持稳定列顺序、点位标识和数值格式；坐标精度应足以唯一标识点位，观测量通常使用 `%.16e` 等稳定格式。打印位数不表示物理精度。
- 字段、单位、布尔编码、注释行以及 NaN 的含义由实际读取器定义，不能用一份“通用 CSV”覆盖不同主题。NaN 仅能表达已声明的不适用项，不能隐藏计算失败。
- 数据区不混入时间戳、机器路径或随机顺序。代码版本、实际配置、环境、命令和复现信息放在已有说明、manifest 或关联审查记录中；未提交代码需有可恢复差异。
- 结果应能逐点核对收敛状态和适用数值检查。使用同一实现导出基线可以保护后续回归，但不能因此声称已通过独立物理验证。

## 候选生成与比较

1. 明确本次应改变和保持不变的行为、点位、观测量与精度依据。
2. 对旧基线运行受影响回归，保留差异；新增基线则先定义消费契约。
3. 使用该主题导出器生成到明确的新候选路径。运行前核对参数与覆盖行为；不要把既有正式基线路径当试验输出。
4. 按点位标识对齐新旧数据，报告新增/删除点和各观测量的绝对、相对差异。近零量使用有依据的绝对误差，失败/缺失点单独列出。
5. 核对差异原因与非变化约束，再选择必要的 unit/integration/regression/validation。整体相关性或文本相似度不能替代数值断言。
6. 候选被接受后更新实际消费者的版本引用，再运行受影响回归。验证与解释写入已有 issue/PR、基线说明或证据入口，不强制创建独立任务单。

小文件可以用 `git diff --no-index -- old.csv candidate.csv` 查看文本变化；退出码 1 表示文件有差异。当前没有统一的数值比较脚本；数值审查使用该主题的字段定义与比较逻辑，不引用不存在的命令。

## 按领域选择入口

根据待维护的基线读取对应领域说明，确认生成参数、数据契约与消费测试。例如，维护输运固定点基线时参阅[输运固定点基线候选](../../scripts/dev/README.md#输运固定点基线候选)；其他领域按各自生成入口和读取器处理。

## 接受、并行修改与保留

接受基线变更需要说明语义/数值原因、受影响点位与字段、新旧差异、应保持不变的约束、实际验证结果及残余风险。源码合入和正式生产权限沿用任务范围，导出成功不授予额外权限。

多个分支同时修改基线时，先对齐代码、配置和数值承诺，再协调候选；不能按文件时间或“最新运行”直接决定采用哪份数据。保留稳定版本标识和来源，不机械地给每个 PR 增加版本号。

被引用的旧版本、冻结证据和兼容性目标继续保留。确需迁移或退役时先检查全部消费引用，保留可恢复版本与说明；不要求每次升级都把旧文件物理搬入 `archived/`。选择性提交本次源码、数据、消费者与说明，保留无关工作。
