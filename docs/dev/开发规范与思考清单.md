# **详细开发规范与实施思考清单**

本部分旨在为开发者在制定详细开发计划时，提供一套超越“如何编码”的完整思考框架，确保功能以**高质量、可维护、可协作**的方式实现。

---

## **一、 需求与设计理解阶段**
在动手写代码之前，必须彻底澄清以下问题：

1.  **功能逻辑闭环**
    *   我能否用简单的语言向他人（产品、测试、其他开发）清晰描述这个功能的完整流程？
    *   所有**正向流程**是否都已明确？边界条件和**异常流程**（如网络失败、数据为空、用户中断、服务降级）是否都已定义并设计了处理方案？
    *   用户操作的**反馈机制**（加载中、成功/失败提示、结果刷新）是否明确？

2.  **交互与数据细节**
    *   UI设计稿/原型中所有状态（初始、加载、成功、错误、空数据）是否都已标注？
    *   **前端与后端的数据契约（API合同）** 是否已明确并达成一致？包括：
        *   请求/响应字段、类型、是否必填、枚举值含义。
        *   分页、排序、筛选的规则。
        *   错误码的统一格式和含义。
    *   本次开发会**新增、修改或删除**哪些数据库表/字段？变更的DDL语句是什么？

3.  **非功能性需求的确认**
    *   **性能要求：** 关键接口的预期响应时间是多少？是否有压测目标（如QPS、TPS）？
    *   **数据权限：** 功能涉及的数据，是否需要根据用户角色、部门等进行行级或列级权限控制？如何实现？
    *   **兼容性要求：** 是否需要支持多浏览器、多终端、特定的老版本APP或API？

4.  **任务拆解与依赖识别**
    *   我能否将这个开发任务进一步拆分为更小的、可独立验证的**子任务**？（例如：1. 建表；2. 实现核心服务层；3. 实现API接口；4. 集成前端组件）
    *   这些子任务之间的**依赖关系**是什么？（例如：必须先完成服务层，才能开发API；API合同确定后，前后端可并行）
    *   我**依赖**于谁？（如：等待设计师提供最终切图、等待其他同事提供某个底层服务接口）
    *   谁**依赖**于我？（如：前端开发在等待我的API、测试在等待我的提测版本）

## **二、 编码实施规范**

1.  **代码结构**
    *   新的代码应该放在项目的哪个目录/模块下？是否符合项目既定的**分层架构**（如Controller-Service-Repository）？
    *   是否需要创建新的类、包或模块？命名是否遵循项目约定，并能清晰体现其职责？

2.  **核心逻辑实现**
    *   **关键算法或业务规则**是否有清晰、可复用的实现方案？是否需要编写单元测试来验证其正确性？
    *   是否存在复杂的**条件分支**？是否可以用策略模式、状态模式等使其更清晰？
    *   如何保证操作的**原子性和数据一致性**？是否需要使用事务？事务的边界在哪里？

3.  **错误与异常处理**
    *   代码中可能抛出哪些**已检查异常**和**运行时异常**？
    *   每种异常应在哪一层被捕获和处理？是记录日志后抛给上层，还是在当前层转化为用户友好的错误信息？
    *   日志记录是否完备？关键信息（如用户ID、操作ID、错误上下文）是否都已打印，便于问题排查？

4.  **安全考量**
    *   所有用户输入是否都经过了**校验和过滤**（防SQL注入、XSS攻击等）？
    *   接口是否需要**身份认证和授权**？当前用户的权限是否已被正确校验？
    *   敏感数据（如密码、手机号）在日志、传输或存储中是否已被**脱敏或加密**？

5.  **并发与性能**
    *   这段代码是否可能在**多线程或分布式环境**下被同时调用？是否存在竞态条件或死锁风险？
    *   是否有**缓存**应用的可能？缓存Key的设计、过期策略和更新策略（Cache-Aside, Write-Through）是什么？
    *   是否存在**慢查询**风险？数据库查询是否用上了合适的索引？

---

## **三、 代码质量与可维护性**

1.  **可读性与可测试性**
    *   函数/方法是否遵循了 **“单一职责原则”** ？是否过长（建议不超过50行）？
    *   变量、函数、类的命名是否**清晰、无歧义**，能直接反映其用途？
    *   代码是否便于**单元测试**？是否有过多的外部依赖（如全局变量、静态方法、直接new对象）？是否可以考虑依赖注入以提高可测试性？

2.  **复用与重构**
    *   项目中是否已有**类似功能的代码**？是应该复用、重构公共组件，还是本次允许一定程度的重复？
    *   本次改动是否会**破坏现有功能**？如何验证？（回归测试）
    *   本次开发是否暴露了现有代码的**坏味道**（如重复代码、过大的类）？是否有必要和可能在本任务内进行小范围重构？

3.  **文档与注释**
    *   **代码注释**：复杂的业务逻辑或算法是否需要添加注释来解释 **“为什么”** 这么做？（避免注释“做了什么”）
    *   **接口文档**：API的Swagger/OpenAPI文档是否需要同步更新？
    *   **变更说明**：数据库变更、核心配置变更是否需要更新相应的README或Wiki？

---

## **四、 团队协作与交付**

1.  **版本控制**
    *   **分支策略**：应该从哪个主干分支（如`develop`）创建特性分支？分支命名是否遵循团队规范（如`feat/xxx`, `fix/xxx`）？
    *   **提交信息**：每次提交的信息是否清晰，能概括本次更改的内容？（推荐使用Conventional Commits格式）

2.  **代码审查（Code Review）**
    *   在提交PR/MR前，我是否已**自行审查**过代码，并运行了本地测试？
    *   PR的描述是否清晰，包含了**功能背景、改动点、测试方案**，并关联了相关任务单（Jira Issue等）？
    *   我计划邀请哪些同事作为**审查者**？他们是否是合适的领域负责人？

3.  **持续集成**
    *   我的代码提交是否能通过CI流水线的**自动检查**（如编译、静态代码分析、单元测试）？
    *   是否需要为本次改动**新增或更新**自动化测试用例（单元测试、集成测试）？

4.  **发布准备**
    *   本次功能上线是否需要**数据库迁移脚本**？脚本是否经过评审，并包含回滚语句？
    *   是否有新的**配置文件或环境变量**需要添加？是否已和运维/配置管理人员确认？
    *   功能上线后，是否需要配置相应的**业务监控**和**告警指标**？

### **【个人开发计划检查清单】**
在制定详细开发计划时，请用以下问题自查：

- [ ] **需求清晰**：我能复述功能的所有主流程、异常场景和非功能要求。
- [ ] **任务拆解**：我已将大任务拆分为小于2天的子任务，并明确了依赖。
- [ ] **设计就绪**：技术方案、API合同、数据模型变更已与相关方确认。
- [ ] **安全合规**：已考虑输入校验、权限控制与数据安全。
- [ ] **质量保障**：已规划关键逻辑的单元测试，并考虑了代码结构。
- [ ] **协作就绪**：知道分支策略、审查者和需要更新的文档。
- [ ] **发布就绪**：已考虑数据库脚本、配置变更和监控需求。

**核心思想**：制定开发计划不仅是排期，更是通过系统性思考，将“完成编码”的目标，提升为“交付一个健壮、可扩展、易于协作的软件组件”。
