# Julia_RelaxTime 的 Codex 高阶使用手册

本手册面向本仓库内使用 Codex 的开发者，目标不是介绍通用 AI 概念，而是把 Codex 放进 `Julia_RelaxTime` 的实际工作流里，让其在物理模拟计算后端、未来前端契约、论文协作三个方向上稳定地产出可审计结果。

本文聚焦三件事：

- 推荐补充到 `AGENTS.md` 的项目约束
- 最值得新增的自定义 skill 设计
- 面向后端开发、前端契约、论文协作的提示模板

## 1. 使用定位

在本仓库中，Codex 最适合承担以下类型工作：

- 读取既有架构与测试分层后，完成小到中等规模实现
- 在不破坏既有物理语义与统一入口契约的前提下做局部重构
- 维护 API 文档、开发文档、实验记录与结果说明的一致性
- 基于既有基线与脚本完成可复现的数值验证与治理

不建议把 Codex 当作“自由发挥的研究助手”。更有效的方式是：

- 先给边界，再给目标
- 先给验收条件，再给实现空间
- 能固化成文档/skill 的，不靠反复口头解释

## 2. 推荐的 AGENTS.md 增补项

下面这些内容适合补入仓库根 `AGENTS.md`。目标是减少多轮对话中的上下文漂移，并把高频协作规则制度化。

### 2.1 任务执行模式约束

建议增加如下规则：

- 涉及 `src/models/`、`src/relaxtime/`、`src/simulation/` 的代码改动时，先阅读相关入口文件与对应测试层，再实施修改。
- 涉及统一求解链路的改动，默认不得改变 mixed-meson governance 与 non-fixedmu unified joint-solve 语义；若确需改变，必须在回复中明确指出。
- 对于跨模块重构，默认先做最小收口改动，再决定是否抽象公共层；避免一次引入新的大抽象。
- 当用户未明确要求“只分析”时，优先直接落地实现、验证并汇报，不停留在方案阶段。

### 2.2 数值与回归治理约束

建议增加如下规则：

- 涉及数值结果、扫描逻辑、求解器路径、截面与弛豫时间链路的修改时，优先判断需要补哪一层测试：`unit`、`integration`、`regression`、`validation`。
- 若改动可能引起数值漂移，默认补充或运行对应 regression；若未补，必须说明原因与风险。
- 不允许为了“让测试通过”随意放宽容差；调整容差时必须说明误差来源、物理含义与验证证据。
- 性能优化类改动默认需要 profiling、benchmark 或现有性能证据支撑；无证据时避免大幅改写热路径。

### 2.3 文档与论文协作约束

建议增加如下规则：

- 稳定入口、脚本契约、前后端数据契约发生变化时，必须同步评估是否更新 `docs/api/`、`docs/dev/`、`docs/guides/`。
- 论文相关写作默认不得虚构实验结论、数值趋势、图表来源或文献结论；只能基于仓库中的代码、结果文件、图表与明确提供的参考资料写作。
- 当任务涉及“方法描述”“实验设置”“图注”“caption”“结果解释”时，先检查术语、变量名、单位与代码实现是否一致，再生成文本。

### 2.4 前端契约约束

建议增加如下规则：

- 前端相关任务在未明确要求 UI 实现前，优先交付后端契约文档、字段定义、单位说明、示例 payload、错误模型。
- 任何面向前端暴露的数值字段，默认明确其单位、取值域、缺失语义、异常语义与排序方式。
- 若接口尚未稳定，优先输出 mock contract 或中间契约文档，而不是直接固化前端实现。

### 2.5 结果沉淀约束

建议增加如下规则：

- 同类高频需求重复出现三次以上时，优先建议沉淀为 skill、脚本入口或模板文档。
- 复杂任务完成后，如形成可复用流程，优先更新 `docs/dev/` 或对应 skill 说明，而不是仅在对话中汇报。

## 3. 最值得新增的自定义 skill 设计

下面给出 5 个优先级最高、最贴合本仓库的 skill 设计。它们都应服务于“减少重复说明、提高结果可复现性、降低跨方向协作成本”。

### 3.1 `transport-regression-keeper`

适用场景：

- 截面、弛豫时间、散射率、输运工作流改动
- baseline 更新与回归门禁补齐
- 出现“数值变了，但不知道是修复还是退化”的情况

核心职责：

- 识别改动影响到的 `unit/integration/regression/validation` 层
- 运行最小必要测试与回归入口
- 对比 baseline、容差、输出摘要
- 生成一段简洁的“数值漂移说明”

建议输入：

- 改动模块
- 预期影响范围
- 是否允许更新 baseline
- 目标 profile（smoke/core/full）

建议输出：

- 执行了哪些命令
- 哪些点位有变化
- 变化是否在容差内
- 是否需要更新 regression 文档或基线文件

### 3.2 `frontend-contract-author`

适用场景：

- 未来前端截面开发前的接口准备
- 单点求解、扫描任务、结果展示的数据契约设计
- 输出 JSON/CSV/表格结构定义

核心职责：

- 从现有脚本入口、模型入口和输出文件中抽取稳定契约
- 形成字段表、单位表、错误语义、示例 payload
- 指出哪些字段已稳定，哪些仍属内部实现细节
- 必要时补 `docs/api/` 或 `docs/dev/` 契约文档

建议输入：

- 面向哪个前端页面或交互流程
- 目标后端入口
- 是否需要 mock response

建议输出：

- 请求 schema
- 响应 schema
- 字段解释与单位说明
- 前端必须处理的边界状态

### 3.3 `paper-traceable-coauthor`

适用场景：

- 论文方法、实验设置、结果描述、图注、附录说明
- 代码实现与论文表述一致性检查
- 从结果文件生成文字草稿

核心职责：

- 仅基于可追溯材料写作
- 抽取方法链路、参数来源、图表含义
- 标记哪些句子是事实陈述，哪些是解释性表述
- 检查符号、单位、变量名、图号引用是否一致

建议输入：

- 目标章节或段落类型
- 相关源码路径
- 相关结果表/图/草稿
- 允许的写作粒度

建议输出：

- 可直接进入论文的中文草稿
- 证据来源列表
- 需要作者自行确认的未闭环点

### 3.4 `experiment-logbook-append`

适用场景：

- 参数扫描
- 异常点复测
- 阈值邻域补点
- 每轮实验的结论追踪

核心职责：

- 按 append-only 方式记录实验台账
- 不重写旧结论，只新增本次实验记录
- 统一记录命令、输入、输出路径、关键观察、后续动作

建议输入：

- 任务标题
- 执行命令
- 输出目录
- 关键观察

建议输出：

- 追加后的台账条目
- 后续建议动作

### 3.5 `codex-task-harness`

适用场景：

- 任务较大、跨后端/文档/前端契约/论文的混合型工作
- 需要先拆分、再实施、再验证

核心职责：

- 先把需求整理成边界、目标、风险、验证方式
- 根据任务类型自动推荐使用哪些现有 skill
- 生成一次性高质量提示词骨架

建议输入：

- 用户任务描述
- 期望输出物
- 可改目录
- 验收条件

建议输出：

- 任务边界
- 推荐执行顺序
- 推荐测试/文档更新项
- 一段可直接发送给 Codex 的任务提示

## 4. 提示模板

下面的模板都刻意偏工程化，重点是边界、契约、验证，而不是“写得像 prompt”。

### 4.1 后端开发模板

适用于 Julia 数值后端、模型入口、求解器链路、脚本收口、测试补齐。

```text
请在 Julia_RelaxTime 仓库中处理这个后端任务：

任务目标：
- <用一句话写清要改什么>

工作边界：
- 允许修改：<目录或文件>
- 不要修改：<目录或文件>
- 必须保持不变的契约：<例如 Models 统一入口 / mixed-meson governance / non-fixedmu joint-solve 语义>

实施要求：
- 先阅读相关入口、调用链和对应测试，再动手
- 优先做最小必要改动，不先引入新抽象
- 若涉及公开稳定入口，评估并更新 docs/api/
- 若涉及数值行为变化，说明是否需要 regression/validation

验证要求：
- 至少运行：<具体测试命令>
- 如果不运行某项测试，说明原因
- 汇报时给出：修改文件、验证结果、残余风险
```

### 4.2 前端契约模板

适用于“先做接口与数据契约，不急着做 UI”。

```text
请为 Julia_RelaxTime 的前端使用场景整理后端契约，不实现 UI。

目标场景：
- <例如：相图扫描结果展示 / 截面查询页 / 单点求解表单>

请完成：
- 梳理可复用的后端入口或脚本入口
- 输出请求参数表、响应字段表、单位说明、错误语义
- 给出 1 到 2 个最小示例 payload
- 标注哪些字段可以视为稳定契约，哪些仍是内部实现细节

工作边界：
- 优先基于 Models 统一入口、现有 scripts 和 docs/api
- 不设计视觉界面
- 不虚构尚不存在的后端能力；若需要新增接口，明确标注为建议项

交付形式：
- 生成或更新 docs/dev/ 或 docs/api/ 下的契约文档
- 汇报时说明前端最需要关注的边界状态
```

### 4.3 论文协作模板

适用于方法段落、实验设置、图注、结果说明、术语统一。

```text
请协助 Julia_RelaxTime 的论文写作，只基于可追溯材料工作。

写作目标：
- <例如：方法小节 / 图3 caption / 实验设置草稿 / 结果讨论初稿>

证据范围：
- 源码：<相关路径>
- 结果文件：<相关路径>
- 图表：<相关路径>
- 现有草稿：<相关路径，可选>

写作要求：
- 不补写仓库中没有证据支持的结果或结论
- 先检查变量名、单位、术语与实现是否一致
- 若发现证据不足、结论跳跃或图文不一致，先列出问题再写
- 输出语言：中文

交付形式：
- 先给结构化提纲
- 再给可直接编辑的正文草稿
- 最后列出需要作者确认的点
```

## 5. 推荐使用顺序

对于本仓库，建议默认按下面顺序组织 Codex 使用方式：

1. 先把长期规则写进 `AGENTS.md`
2. 把重复三次以上的高频任务沉淀成 skill
3. 用 `docs/dev/` 保存团队内部协作手册、契约文档、执行规范
4. 用 `docs/api/` 保存稳定对外入口与数据契约
5. 用测试与基线作为最终裁判，而不是仅靠对话判断“看起来没问题”

## 6. 最小落地建议

如果只做一轮最小增强，建议优先落地以下三件事：

1. 在 `AGENTS.md` 增补“数值回归治理”“前端契约优先”“论文不得虚构证据”三组规则。
2. 新增 `frontend-contract-author` 与 `paper-traceable-coauthor` 两个 skill 设计草案。
3. 后续所有涉及大任务的 Codex 请求，都先使用本手册中的模板下发。

这样能最快提升 Codex 在本仓库中的稳定性与复用率。
