# 代码审查指南

## 概述

本文档定义QCD模型库项目的代码审查流程、检查清单和最佳实践，确保代码质量、可维护性和团队知识共享。

**目标**：通过系统化的代码审查提高代码质量，传播最佳实践，促进团队协作。

---

## 1. 审查流程

### 1.1 何时需要审查

**必须审查**：
- 所有合并到`develop`或`main`的Pull Request
- 涉及核心架构变更的代码
- 新增公共API或修改现有API
- 性能关键路径的优化
- 复杂的算法实现

**可选审查**：
- 纯文档更新（但推荐审查）
- 测试代码（但推荐审查）
- 个人实验分支

### 1.2 审查者选择

**审查者类型**：

1. **核心审查者**（必需）
   - 熟悉项目架构的核心开发者
   - 至少1人审查并批准

2. **领域专家**（按需）
   - **物理学家**：涉及物理公式、模型实现
   - **性能专家**：涉及性能优化、数值算法
   - **架构师**：涉及架构设计变更

3. **自动审查**（始终）
   - CI/CD流水线检查
   - 静态分析工具
   - 测试覆盖率报告

**选择标准**：
- 审查者应熟悉相关代码模块
- 审查者应有足够时间（24-48小时内响应）
- 避免自己审查自己的代码

### 1.3 审查时间线

| 阶段 | 时间要求 | 说明 |
|------|---------|------|
| PR创建 | 立即 | 作者创建PR并请求审查 |
| 首次响应 | 24小时内 | 审查者确认收到并给出初步反馈 |
| 详细审查 | 48小时内 | 审查者完成详细审查并提供意见 |
| 作者响应 | 24小时内 | 作者回应审查意见并更新代码 |
| 最终批准 | 48小时内 | 审查者批准或请求进一步修改 |

**紧急情况**：
- Hotfix可以缩短时间线（但仍需审查）
- 关键bug修复优先级最高

## 2. 审查检查清单

### 2.1 代码质量

#### 可读性
- [ ] 变量、函数、类型命名清晰且符合Julia命名约定
- [ ] 函数长度合理（推荐<50行，最多<100行）
- [ ] 复杂逻辑有注释说明"为什么"而非"做什么"
- [ ] 代码结构清晰，逻辑流程易于理解
- [ ] 避免过度嵌套（最多3层）

#### 设计原则
- [ ] 遵循单一职责原则（每个函数只做一件事）
- [ ] 避免代码重复（DRY原则）
- [ ] 适当的抽象层次（不过度抽象也不过度具体）
- [ ] 依赖注入而非硬编码依赖
- [ ] 接口清晰，职责明确

#### Julia特定
- [ ] 类型稳定性（使用`@code_warntype`检查）
- [ ] 适当使用多重分派
- [ ] 避免类型不稳定的容器（如`Vector{Any}`）
- [ ] 性能关键函数使用`@inline`、`@inbounds`
- [ ] 避免全局变量（使用`const`或函数参数）

### 2.2 正确性

#### 逻辑正确性
- [ ] 算法实现与设计文档一致
- [ ] 边界条件处理正确
- [ ] 错误处理完整（所有可能的异常路径）
- [ ] 数值计算稳定（避免除零、溢出、下溢）
- [ ] 物理约束得到满足

#### 测试覆盖
- [ ] 新功能有对应的单元测试
- [ ] 测试覆盖主要代码路径
- [ ] 测试包含边界情况和错误情况
- [ ] 测试名称清晰描述测试内容
- [ ] 测试独立且可重复

### 2.3 性能

#### 性能考虑
- [ ] 避免不必要的内存分配
- [ ] 循环中避免重复计算
- [ ] 使用合适的数据结构
- [ ] 考虑了类型推断和编译器优化
- [ ] 性能关键代码有基准测试

#### 性能验证
- [ ] 运行性能基准测试
- [ ] 与基线对比（如适用）
- [ ] 性能降低<5%（如有降低需说明原因）
- [ ] 内存使用合理

### 2.4 安全性

#### 输入验证
- [ ] 所有用户输入经过验证
- [ ] 参数范围检查
- [ ] 类型检查（如需要）
- [ ] 物理约束验证

#### 错误处理
- [ ] 使用自定义异常类型
- [ ] 错误消息清晰且有帮助
- [ ] 异常在适当的层级处理
- [ ] 日志记录充分

### 2.5 文档

#### 代码文档
- [ ] 公共函数有完整的docstring
- [ ] Docstring包含参数说明、返回值、示例
- [ ] 复杂算法有注释说明
- [ ] 物理公式有引用或说明

#### 外部文档
- [ ] API文档已更新（如适用）
- [ ] 用户指南已更新（如适用）
- [ ] CHANGELOG已更新
- [ ] 迁移指南已更新（如有breaking changes）

### 2.6 向后兼容性

#### 兼容性检查
- [ ] 没有破坏现有公共API
- [ ] 如有breaking changes，已在CHANGELOG中说明
- [ ] 提供了迁移路径
- [ ] 现有测试仍然通过

### 2.7 架构一致性

#### 架构遵循
- [ ] 符合项目分层架构
- [ ] 依赖方向正确（不违反依赖规则）
- [ ] 使用了适当的抽象接口
- [ ] 代码放在正确的模块/目录

## 3. 审查类型

### 3.1 快速审查（<30分钟）

**适用场景**：
- 小型bug修复（<50行）
- 文档更新
- 测试补充
- 配置文件修改

**检查重点**：
- 逻辑正确性
- 测试通过
- 文档同步

### 3.2 标准审查（1-2小时）

**适用场景**：
- 新功能实现（<500行）
- 重构现有代码
- 性能优化
- API变更

**检查重点**：
- 完整的检查清单
- 设计合理性
- 测试覆盖率
- 性能影响

### 3.3 深度审查（>2小时）

**适用场景**：
- 大型特性（>500行）
- 架构变更
- 核心算法实现
- 安全关键代码

**检查重点**：
- 架构设计审查
- 详细的代码审查
- 性能基准测试
- 安全性分析
- 可能需要多轮审查

## 4. 审查意见分类

### 4.1 意见级别

**🔴 必须修改（Blocker）**：
- 严重bug或逻辑错误
- 安全问题
- 破坏性的API变更未说明
- 测试失败
- 违反架构原则

**🟡 强烈建议（Major）**：
- 性能问题
- 代码质量问题
- 测试覆盖不足
- 文档缺失
- 命名不清晰

**🟢 建议改进（Minor）**：
- 代码风格问题
- 可读性改进
- 注释补充
- 小的重构建议

**💡 讨论（Question）**：
- 设计选择的讨论
- 替代方案的探讨
- 学习性问题

### 4.2 意见格式

**推荐格式**：
```markdown
**[级别] 位置：问题描述**

详细说明...

建议：具体的改进建议

示例代码（如适用）：
```julia
# 建议的代码
```
```

**示例**：
```markdown
**🔴 src/models/pnjl.jl:45 - 类型不稳定**

函数`calculate_mass_vec`返回类型不稳定，可能导致性能问题。

建议：明确返回类型为`SVector{3, Float64}`

```julia
function calculate_mass_vec(φ::SVector{3, T}) where {T} :: SVector{3, T}
    # ...
end
```
```

## 5. 审查最佳实践

### 5.1 作为审查者

**DO（应该做）**：
- ✅ 及时响应审查请求
- ✅ 提供建设性的反馈
- ✅ 解释"为什么"而不只是"做什么"
- ✅ 提供具体的改进建议和示例
- ✅ 认可好的代码和设计
- ✅ 保持友好和专业的语气
- ✅ 如果不确定，提出问题而非断言

**DON'T（不应该做）**：
- ❌ 拖延审查
- ❌ 只说"不好"而不给建议
- ❌ 过于挑剔代码风格
- ❌ 在审查中引入个人偏好
- ❌ 使用攻击性语言
- ❌ 要求完美（追求"足够好"）

### 5.2 作为作者

**DO（应该做）**：
- ✅ 提供清晰的PR描述
- ✅ 自我审查后再请求审查
- ✅ 保持PR大小合理（<500行）
- ✅ 及时响应审查意见
- ✅ 解释设计决策
- ✅ 感谢审查者的时间和反馈
- ✅ 虚心接受建议

**DON'T（不应该做）**：
- ❌ 提交未测试的代码
- ❌ 在一个PR中混入多个不相关的改动
- ❌ 忽视审查意见
- ❌ 防御性地回应批评
- ❌ 在未解决意见的情况下强行合并

### 5.3 审查对话

**良好的审查对话示例**：

```
审查者：这里的循环可以用向量化操作替代，性能会更好。
作者：好建议！我会改用广播操作。不过这部分不在性能关键路径上，
      改动会影响可读性吗？
审查者：你说得对，这里可读性更重要。保持现在的写法就好。
```

**不良的审查对话示例**：

```
审查者：这代码写得不好。
作者：哪里不好？
审查者：就是不好。
```

## 6. 特定场景的审查重点

### 6.1 物理模型实现

**额外检查**：
- [ ] 物理公式与参考文献一致
- [ ] 单位转换正确
- [ ] 物理约束得到满足
- [ ] 数值稳定性（避免奇点、发散）
- [ ] 与已知结果对比验证

**审查者**：需要物理学家参与

### 6.2 性能优化

**额外检查**：
- [ ] 运行性能基准测试
- [ ] 与优化前对比
- [ ] 性能提升量化（如提升20%）
- [ ] 没有引入正确性问题
- [ ] 代码可读性仍然可接受

**审查者**：需要性能专家参与

### 6.3 API变更

**额外检查**：
- [ ] API设计合理且一致
- [ ] 向后兼容或提供迁移路径
- [ ] API文档完整
- [ ] 使用示例清晰
- [ ] 考虑了未来扩展性

**审查者**：需要架构师参与

### 6.4 重构

**额外检查**：
- [ ] 重构目标明确
- [ ] 行为保持不变（回归测试通过）
- [ ] 代码质量确实提升
- [ ] 没有引入新的复杂性
- [ ] 分步进行，每步可验证

**CI/CD检查**：

- 类型稳定性检查（JET.jl）
- 依赖循环检测

**代码质量**：
- 复杂度分析
- 重复代码检测

**本地测试**：
```bash

```

**代码审查辅助**：
- GitHub PR界面
- 本地diff工具
- IDE的代码导航功能

## 10. 常见问题

### Q1: PR太大怎么办？

**A**: 
- 建议作者拆分PR（<500行）
- 如果无法拆分，安排多轮审查
- 重点审查核心逻辑，次要部分快速审查

### Q2: 审查意见有分歧怎么办？

**A**:
- 通过讨论达成共识
- 如果无法达成，升级到架构师或团队负责人
- 记录决策和原因（ADR）

### Q3: 紧急修复如何审查？

**A**:
- 仍然需要审查，但可以缩短时间线
- 优先级最高，审查者应立即响应
- 可以先合并后补充审查（极端情况）

### Q4: 审查者不熟悉代码怎么办？

**A**:
- 作者提供更详细的PR描述和背景
- 审查者可以请求额外的审查者
- 审查者可以提出学习性问题
