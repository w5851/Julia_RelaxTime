# 代码审查指南

审查重点是实现是否满足目标、验证是否捕获真实错误、变化是否影响调用方。审查深度随数值和工作流风险调整。

## 每次审查的核心问题

1. 变更是否解决了明确的问题，范围是否与需求一致？
2. 入口、参数、返回值、单位和错误语义是否正确？
3. 是否保留了要求不变的行为、用户改动和正式结果？
4. 现有验证能否发现本次变化可能引入的实际错误？
5. 哪些稳定契约或文档需要随之更新？

## 按风险选择审查与验证

| 变化 | 关注点 |
| --- | --- |
| 文档、导航、显示措辞 | 事实、链接、实际合同及最终可读性 |
| helper、校验器、内部重构 | 受影响行为和边界；已有覆盖足够时复用 |
| Models/工作流/CLI/HTTP | 有效参数、字段与单位、最短跨模块链和失败行为 |
| 公式、solver、积分或分支 | 假设、符号、归一化、极限、回归差异和数值误差 |
| 性能优化 | 已有瓶颈证据、前后测量及行为一致性 |
| 正式结果交付 | 适用的收敛、来源和产物完整性证据 |

没有统一的代码覆盖率百分比、新增单测数量、审查时长或 PR 行数门槛。新增测试应覆盖真实缺陷、新行为或具体缺口；删除/调整测试应说明原断言的验证价值及重要覆盖是否仍在。

源码里的名称和措辞通常属于实现细节；仅检查字符串存在不能证明对应行为执行。真正的架构禁用规则可由静态检查承担。任务当前状态、分支和 SHA 不作为软件的固定回归答案。

## 反馈与完成

反馈指出具体文件、触发条件、影响和建议动作。优先处理正确性、数据破坏和稳定契约问题，风格建议按维护收益选择。

保留有用的作者/领域审查；审批人数、required checks 以实际 GitHub 配置为准。普通修复不要求另找多个领域专家，涉及未决物理约定或论文结论时保留必要的作者决策。

审查完成后简要报告变化、相关验证及未解决项。已充分验证时停止扩大检查。
