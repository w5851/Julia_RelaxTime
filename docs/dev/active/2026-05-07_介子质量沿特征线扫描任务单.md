# 介子质量沿特征线扫描任务单

更新日期：2026-05-07

当前状态：实施中；已在 `src/models/scans/` 与 `Models` 统一入口层落下第一版最小可用实现，当前继续补测试、API 文档与任务单验收口径。

> 目的：把“沿特征线扫描介子质量”从临时脚本想法收束成正式、可复用、可验证、可扩展的扫描能力，而不是继续在单一网格脚本上叠加特判。

---

## 1. 背景与目标

当前仓库在介子质量与路径扫描方向已经分别具备：

- [x] 介子单点求解 workflow：
  - `Models.solve_gap_and_meson_point`
- [x] 基于规则网格的介子质量扫描脚本：
  - `scripts/relaxtime/run_gap_meson_mass_scan.jl`
- [x] chemical freeze-out 参数化、path profile 与正式扫描入口：
  - `Models.run_freezeout_fixedmu_scan`
  - `Models.run_freezeout_meson_density_scan`
  - `src/models/scans/FreezeoutProfiles.jl`
  - `src/models/scans/FreezeoutPathProfiles.jl`
- [x] crossover / 外部路径驱动的介子数密度正式扫描入口：
  - `Models.run_crossover_meson_density_scan`
  - `Models.run_external_path_meson_density_scan`
- [x] solver 层已有固定比熵约束模式：
  - `FixedSigma`

但当前仍缺一条正式的“介子质量沿特征线扫描”主线：

- [ ] 介子质量扫描目前仍主要停留在规则网格脚本层
- [ ] 尚无面向介子质量的等熵线扫描正式入口
- [ ] 尚无面向介子质量的 chemical freeze-out 路径扫描正式入口
- [ ] 尚无统一的“路径生成 / 路径 profile / 路径点扫描”抽象，可同时服务不同 meson workflow
- [ ] 尚无对应的 regression / plot-review / data-layer 治理口径

本任务单的目标是：

1. 固化“沿特征线扫描介子质量”的范围、入口与输出合同；
2. 至少覆盖等熵线与 chemical freeze-out 两类路径；
3. 明确该能力应优先落在 `src` 的高层扫描抽象，再由脚本包装；
4. 为后续 meson density / meson pressure / EOS 复用同一条路径能力预留接口。

## 4. 需求收口

### 4.1 目标能力

本期希望形成的正式能力是：

- [x] 沿等熵线扫描介子质量
- [x] 沿 chemical freeze-out 路径扫描介子质量
- [x] 输出统一 CSV，记录路径标签、点位定义、平衡态诊断与介子质量结果
- [x] 为后续 path-driven meson density / EOS 提供可复用的最小路径扫描壳（未扩展为更大共享 framework）

### 4.2 路径家族最小集合

第一版至少覆盖：

- [ ] `isentropic`
  - 输入核心为目标 `sigma = s / n_B`
  - 路径生成需要明确定义温度窗口、步长/采样数、continuation 与失效点处理
- [ ] `freezeout`
  - 复用现有 freeze-out baseline 与 path profile 体系
  - 允许直接消费 `FreezeoutProfiles` / `FreezeoutPathProfiles`

当前建议口径：

- [x] 第一版不强行把所有路径折叠为单一黑箱公式
- [x] 路径 baseline 与“最终扫描路径 profile”应继续分开治理
- [x] 等熵线与 freeze-out 共用的是“路径点列扫描壳”，不是同一条物理参数化公式

### 4.3 放在脚本层还是更高抽象层

当前建议结论：

- [x] **主能力应放在 `src/models/scans/` 的更高抽象层**
- [x] **脚本层只做 CLI 参数解析、profile 选择、输出路径与 README/provenance 组织**

原因：

- [x] 仓库已对 freeze-out 能力采用 `src` 抽象，而不是把路径逻辑硬编码在脚本中
- [x] 等熵线与 freeze-out 至少是两类路径家族，若仅放脚本层会复制 continuation、排序、CSV、失败行处理等样板
- [x] 后续 meson density / pressure / EOS 很可能复用相同路径点列，不应把路径展开逻辑绑死在单一脚本里
- [x] `Models` 层当前正是统一入口治理面，符合仓库“统一入口请使用 Models 与 src/models/entrypoints.jl”的约束

补充判断：

- [ ] 若只是一次性分析图或文献临时复现，脚本层可接受；
- [x] 但本需求已经明确为“能力固化”，因此默认按 `src` 正式入口设计。

## 5. 建议抽象方案

### 5.1 推荐分层

建议沿用 freeze-out 已验证过的三层/四层结构：

1. 路径 baseline / profile 层  
   - 负责定义“这条线是什么、有哪些参数、如何从配置读取”
2. 路径点列生成层  
   - 负责把 profile 展开为有序 `(T_MeV, muB_MeV, path_label, order_key, ...)` 点列
3. meson-mass path scan 层  
   - 负责 continuation、逐点求解、CSV 行写出、失败恢复
4. script/CLI 层  
   - 负责把 profile 名称、输出路径、数值选项暴露给用户

### 5.2 建议模块方向

第一版建议至少考虑以下模块形态：

- [x] `src/models/scans/IsentropicPathProfiles.jl`
  - 当前以最小 profile/点列生成器管理 fixed-`σ` 路径
- [x] `src/models/scans/MesonMassPathScan.jl`
  - 已统一承接 path-driven meson mass scan
- [x] `src/models/entrypoints.jl`
  - 已暴露 `Models.run_meson_mass_path_scan(...)`

freeze-out 复用途径有两种可选策略：

- [ ] 方案 A：`MesonMassPathScan` 直接消费 `FreezeoutPathProfiles.build_freezeout_path_points`
- [ ] 方案 B：再抽一个更通用的 path-point contract，让 freeze-out / isentropic 都输出同构点列

当前偏好：

- [x] 先走 **方案 A 或 A→B 的最小收敛路径**
- [x] 先复用现有 freeze-out 点列 contract，避免一上来做过大的跨模块泛化

### 5.3 与现有网格脚本的关系

- [x] `run_gap_meson_mass_scan.jl` 保留为规则网格入口
- [ ] 新增 path-driven 入口，不改写旧脚本语义
- [ ] 当 path-driven 入口稳定后，再考虑是否让旧脚本的一部分 CSV/row 逻辑下沉复用

## 10. 风险与回退

- [ ] 风险：一开始就做过度泛化的“万能路径框架”，范围失控
  - 回退：先让 freeze-out 复用现有 contract，等熵线单独补最小 profile
- [ ] 风险：把路径逻辑只放脚本层，后续 meson density / EOS 再次复制
  - 回退：第一版就把路径点列与扫描执行下沉到 `src/models/scans/`
- [ ] 风险：等熵线数值求解比 freeze-out 更敏感，导致 smoke 不稳定
  - 回退：先锁轻量 canonical case，再逐步扩重路径
