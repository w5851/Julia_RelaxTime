## 2. 目录与模块放置决策

结论：源码建议放入 src/models/phase，而不是 analysis。

理由：
- phase 比 analysis 更具体，语义直接对应相图相变能力域。
- 该域未来会承载 pipeline、CEP 规则、产物合同、报告输出，不只是“分析函数集合”。
- 与 scans、workflows 同层级，便于治理边界。

建议结构：

- src/models/phase/PhaseCore.jl
  - 纯算法：detect_s_shape、maxwell_construction、曲线预处理
- src/models/phase/CEPDetector.jl
  - CEP bracket + 二分细化 + 失效策略
- src/models/phase/CrossoverLine.jl
  - detect_crossover、scan_crossover_line（通过 Models 入口）
- src/models/phase/PhasePipeline.jl
  - 端到端产线编排（scan -> phase analysis -> artifacts）
- src/models/phase/PhaseArtifacts.jl
  - CSV/JSON/Markdown 报告落盘与 schema 校验
- src/models/phase/PhaseTypes.jl
  - 结果结构体与数据合同类型

兼容层策略：
- src/models/pnjl/analysis/PhaseTransition.jl 在过渡期保留导出，但内部转发到 src/models/phase。

## 3. 数据产物位置与合同

### 3.1 放置位置

- 可复用相图数据（默认落盘）：data/processed/<model_kind>/phase_diagram/
- 稳定参考数据集（可选晋升后写入）：data/reference/<model_kind>/phase_diagram/
- 临时运行产物：data/outputs/results/<model_kind>/phase/

注意（与 CI 基线的区别）：
- data/reference 用于“参考数据集/人工对照/大结果归档”，不直接作为 CI 数值门禁基线。
- CI 数值基线按仓库治理规则存放在 tests/baselines/<domain>/，并通过 tests/unit/<domain>/ 的基线测试进行校验。

数据分层准则：
- processed：可复用运行结果（候选产物），支持反复覆盖与版本演进。
- data/reference：冻结的参考数据集（golden），只接受通过晋升流程的产物。
- outputs：临时调试与一次性运行结果，不作为稳定依赖输入。

建议采用 run_id 子目录：
- data/processed/<model_kind>/phase_diagram/<run_id>/

run_id 默认建议：
- phase_<profile>_<yyyymmdd_HHMMSS>

### 3.2 产物文件

- phase_summary.json
  - CEP、统计、收敛率、配置快照、git commit、生成时间
- first_order_boundary.csv
  - T_MeV, mu_transition_MeV, rho_hadron, rho_quark, area_residual, converged
- spinodal.csv
  - T_MeV, mu_spinodal_hadron_MeV, mu_spinodal_quark_MeV, rho_spinodal_hadron, rho_spinodal_quark
- crossover_line.csv
  - mu_MeV, T_crossover_MeV, rho, method, converged, derivative
- phase_report.md
  - 可读报告（参数、结果摘要、失败点、异常统计）

### 3.3 字段/单位约定

- 对外产物统一使用 MeV（温度、化学势）。
- 内部计算允许使用 fm^-1，但写盘前统一转换。
- 缺失值统一写 NaN，不使用空字符串。
- 所有产物必须包含 xi 字段或在 summary 中声明 xi 固定值。
- phase_summary.json 必须包含：model_kind、model_variant、schema_version、config_hash、run_id。

实现约束补充（2026-03-02）：
- JSON 产物（phase_summary.json）不允许写入 NaN（JSON3 严格模式会报错）；缺失值在 JSON 中统一写 null。
- CSV 产物继续允许使用 NaN 表示缺失值。

### 3.4 产物晋升流程（processed -> reference）

默认流程（你提出的流程）定义为：
1. 先检查 data/reference 是否已有同口径参考数据集（按 model_kind + profile + xi + grid + schema_version 匹配）。
2. 若无可用基线，先完整产出到 processed/<model_kind>/phase_diagram/<run_id>/。
3. 对该 run 执行晋升校验（字段合同、单位合同、必需文件完整性、基线/物理门限检查）。
4. 通过后执行“晋升”：复制或快照写入 data/reference/<model_kind>/phase_diagram/<baseline_id>/，并记录来源 run_id。
5. 未通过则保留在 processed，标记 rejected，不得覆盖 reference。

baseline_id 建议：
- baseline_<profile>_<schema_version>_<config_hash_short>

补充（CI 数值基线导出流程）：
1. 从 processed 的某个 run 里“抽取最小基线子集”（固定点/关键曲线关键点），导出到 tests/baselines/phase/。
2. 在 tests/unit/phase/ 添加基线校验测试，PR 必过放入 unit-smoke。
3. 基线变更需按仓库 baseline 治理规则提交“原因 + 差异摘要 + 验证命令”。

执行约束：
- 默认不在普通 PR 的 CI 中自动执行“晋升到 data/reference”（避免无意写入与变更准入问题）。
- 晋升应走手工命令或专门 workflow（带审批/明确的变更说明）。

说明：
- 这是推荐且合理的治理流程，避免把未审核运行结果直接污染 reference。
- data/reference 不做“首次计算”的落盘目的地，只做“通过评审后的稳定参考库”。
- CI 数值门禁基线不放 data/reference，放 tests/baselines。

## 7. 需要先统一的细节（默认决策）

以下采用默认值推进，若后续有物理口径变更再调整：

- CEP 定义：以“最后存在有效 Maxwell 解的温度”作为主定义。
- 二分停止条件：温度区间宽度与面积残差双阈值。
- 失败策略：单温度失败允许继续，最终在 summary 与 report 标红。
- 输出单位：产物层统一 MeV；内部自由使用 fm^-1。

CEP 策略与前置条件（更新）：
- `cep_strategy=direct`：直接在温度轴做二分，不要求温度切片共享相同 rho 网格；每个评估点可独立重算曲线。
- `cep_strategy=interpolate`：保留历史插值路径，仍要求相邻温度曲线具备可插值前提（通常意味着一致或可映射的 rho 网格）。
- direct 推荐的默认 bracket 策略为 `directional`，并在失败时可回退 `scan`（由 `cep_direct_fallback_scan` 控制）。
- gray-zone（`area_tol_good < area_residual < area_tol_bad`）按 `unknown` 处理，累计为 `unknown_count`，用于质量评估与回归监控。
