# **项目交付物定位与管理规范**

## **一、核心原则**

在制定开发计划时，必须明确每个产出物“存放何处、如何管理”，这直接关系到团队协作效率和项目长期可维护性。请遵循以下核心原则：

1.  **单一真相源：** 任何文档或配置在项目中应**有且只有一个**官方、权威的存放位置，避免信息碎片化和版本冲突。
2.  **与代码同生命周期：** 尽可能让文档、配置、脚本等与它们所描述的代码**一起进行版本控制**，保证变更同步。
3.  **分类清晰，易于检索：** 按类型、模块或功能组织交付物，建立清晰的目录结构。
4.  **自动化与流程集成：** 将交付物的生成、更新与开发流程（如CI/CD）绑定，减少手动维护成本。

---

## **二、主要交付物存放位置详解**

### **1. 代码与直接产物**

| 交付物 | 推荐位置 | 说明与思考问题 |
| :--- | :--- | :--- |
| **源代码** | `src/`, `app/`, 或按模块划分的目录（如 `user/`, `order/`） | • 项目结构是否遵循既定的架构模式？<br>• 新功能模块的代码放在哪个目录下最合理？ |
| **单元测试代码** | 通常与源码对应，如 `src/foo/foo.py` 对应 `tests/foo/test_foo.py` | • 测试文件的结构是否与源码结构保持一致？<br>• 是否便于 `pytest` 或 `jest` 等工具自动发现？ |
| **数据库迁移脚本** | `migrations/` 或 `db/scripts/` | • 脚本命名是否包含时间戳和描述（如 `20240321_add_user_table.sql`）？<br>• 回滚脚本是否一同提供？ |
| **构建产物/打包脚本** | 项目根目录的 `Dockerfile`, `package.json`, `pom.xml`, `build.gradle` | • 构建配置是否已更新，以包含新功能的依赖？<br>• `.dockerignore`、`.gitignore` 是否过滤了不必要的文件？ |

### **2. 文档类**

| 交付物 | 推荐位置 | 说明与思考问题 |
| :--- | :--- | :--- |
| **API接口文档** | **首选：与代码放在一起**（如使用 Swagger/OpenAPI 注解，通过工具自动生成）。<br>**备选：** 项目内的 `/docs/api/` 目录，存放 `openapi.yaml` 等描述文件。 | • **关键思考：** API文档是否**与代码同步更新**？手动维护的文档极易过时。<br>• 是否已集成到CI流程，确保每次构建都生成最新文档？<br>• 前端/外部调用方如何便捷地访问到这份文档？（如部署 Swagger UI） |
| **数据库设计文档** | **首选：** 将 `ER图` 和 `DDL` 脚本放在 `/docs/db/` 目录。<br>**强烈推荐：** 使用版本化的数据库迁移工具（如Flyway, Liquibase），其脚本本身就是设计文档。 | • 是否记录了数据模型的变更历史和原因？<br>• 是否方便在开发、测试、生产环境之间同步结构？ |
| **架构设计/流程图** | `/docs/design/` 或 `/docs/architecture/` | • 文件命名是否清晰（如 `payment_sequence_v2.png`, `system_context.md`）？<br>• 图中是否包含了关键决策的说明？ |
| **部署与运维手册** | `README.md`（基础说明）或 `/docs/deployment/`（详细手册） | • 是否说明了新功能所需的环境变量、配置项？<br>• 是否有健康检查、监控指标等运维相关的说明？ |
| **需求/功能说明** | **（此文档应与代码同仓库）** 在项目根目录或 `/docs/` 下建立功能专属文件，如 `FEATURE_A.md`。 | • 此文档是否描述了该功能的业务背景、验收标准、核心流程？<br>• 是否方便新成员通过阅读此文档和代码快速理解功能全貌？ |

### **3. 配置与资源**

| 交付物 | 推荐位置 | 说明与思考问题 |
| :--- | :--- | :--- |
| **应用配置文件模板** | `/config/` 或 `/conf/` 目录，存放如 `application-template.yaml`, `.env.example` | • **永远不要**将含敏感信息（密码、密钥）的真实配置文件提交到仓库。<br>• 模板文件是否清晰说明了每个配置项的作用和示例？ |
| **静态资源** | `/public/`, `/static/`, `/assets/` | • 图片、字体、前端编译后的CSS/JS应放在哪里？<br>• 是否有CDN或专门的静态文件服务器？开发环境如何引用？ |
| **CI/CD流水线定义** | 项目根目录的 `.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile` | • 流水线是否覆盖了新功能的构建、测试、部署阶段？<br>• 是否需要为新功能添加特有的质量门禁（如专项测试）？ |

### **4. 外部与协作类交付物**

| 交付物 | 推荐位置 | 说明与思考问题 |
| :--- | :--- | :--- |
| **UI设计稿/切图** | **（此为非代码资产）** 推荐使用**设计协作平台**（如Figma, Zeplin），并将**链接**记录在项目Wiki或 `/docs/design/README.md` 中。 | • 如何在开发过程中确保使用的是**最新版本**的设计稿？<br>• 设计标注、组件状态、交互说明是否易于获取？ |
| **项目管理与任务追踪** | **（外部系统）** 如 Jira, Asana, GitHub Issues。必须在**代码提交信息**或**合并请求描述**中关联任务ID（如 `fix: #PROJ-123`）。 | • 代码变更是否可追溯至原始需求和任务？<br>• 任务状态的流转（开发中、测试中、已完成）是否与代码分支状态同步？ |
| **会议记录与决策日志** | 团队共享的**知识库**（如Confluence, Notion）或项目 `/docs/decisions/` 目录下的 `ADR（架构决策记录）` 文件。 | • 重要的技术决策（如“为什么选择技术A而非B”）是否被记录下来？<br>• 这些记录是否方便项目成员事后查阅，避免重复讨论？ |

## **三、制定计划时的思考清单**

在规划开发任务时，请针对你的功能，回答以下问题以明确交付物管理：

- [ ] **代码位置：** 新功能的代码文件应该创建在哪个现有目录下？还是需要新建一个目录？其结构是否符合项目约定？
- [ ] **文档同步：** 哪些文档**必须**随代码更新？
    - API文档 → 我已更新Swagger注解或OpenAPI文件。
    - 数据库变更 → 我已提供迁移脚本，并考虑更新ER图或数据字典。
    - 配置说明 → 我已在 `README` 或 `config` 模板中添加了新配置项说明。
- [ ] **配置与资源：** 新功能需要新增或修改哪些配置文件、环境变量或静态资源？它们应该放在哪里？
- [ ] **外部依赖：** 新功能依赖的设计稿、第三方服务文档、接口协议，其**权威链接**是否已记录在项目内部文档中？
- [ ] **协作流程：** 我的代码分支、提交信息、合并请求描述，是否已正确关联到项目管理工具（Jira等）中的任务？是否方便测试和产品同学回溯？
- [ ] **生成与验证：** 是否有交付物（如API文档、类型定义）可以通过**工具自动生成**？我是否已将生成步骤集成到 `Makefile`、`npm script` 或 CI流程中？

**最终目标**：确保**每一位项目成员**（包括未来的你）都能在统一、可预期的地方，快速找到与任何功能相关的、**最新且准确**的所有交付物。这极大地降低了协作成本和项目维护门槛。
