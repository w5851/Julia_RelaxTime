# AD 编译治理能力画像化设计

## 1. 背景与目标

### 1.1 背景

- 当前 AD/高阶导数相关流程的冷启动耗时由编译主导（典型单测中编译占比约 96%+）。
- 现有优化已引入 sysimage 与 precompile workload，但仍存在“收益未吃满”与“场景覆盖不均”问题。
- 风险点：若按单个测试文件做 workload，后续新增测试/脚本无法自动继承收益。

### 1.2 目标

- 将预编译治理从“文件导向”升级为“能力导向”。
- 确保测试（unit/integration/regression/validation）与脚本（scan/CLI/workflow）共享同一预编译能力基座。
- 建立 trace 增量回收与门禁机制，防止编译回退。

### 1.3 非目标

- 本期不做算法重写（例如高阶导数公式替换）。
- 本期不强行将所有路径压到同一数值配置，仅统一“类型形状与能力入口”。

## 2. 现状证据（关键结论）

- 块级拆解：高阶守恒荷单测冷启动 163.69s，其中编译估算 158.17s（96.6%）。
- sysimage 对不同 AD 场景收益不均：
  - 导数脚本单点约 +40.97%
  - thermo_derivatives 单测约 +19.22%
  - susceptibilities 扫描约 +8.97%
  - 个别高阶单测接近 0 收益
- trace 画像显示剩余热点集中在：
  - `ForwardDiff.Partials{5,Float64}` / `Partials{3,Float64}`
  - `NLSolversBase.OnceDifferentiable(..., ForwardDiff.Chunk{5})`
  - `ForwardDiffStaticArraysExt` 相关生成器/collect 特化

## 3. 设计原则

1) 能力优先：按计算能力组织 workload，而非按测试文件组织。
2) 单一入口：测试 runner、脚本、sysimage 构建使用同一注册表与 profile。
3) 增量闭环：trace 新增签名可回收映射到能力画像。
4) 可治理：有可量化门禁指标（trace 体量、冷启动阈值、画像覆盖率）。
5) 向后兼容：现有命令保持可用，新增能力为增强而非破坏性替换。

## 4. 能力画像模型

### 4.1 能力枚举（第一版）

- `:gap_solver_ad`
  - 目标：求解器 + AD + implicit residual 路径
- `:thermo_derivatives_ad`
  - 目标：`thermo_derivatives` / `mass_derivatives` / `bulk_viscosity_coefficients`
- `:conserved_charge_highorder`
  - 目标：`chi_BQS`、`chi{1..4}_{B,Q,S}`、`cumulant_BQS`、`baryon_*`
- `:phase_cli_scan`
  - 目标：phase CLI 典型 scan/manifest 路径
- `:transport_workflow`
  - 目标：transport workflow 入口与关键衍生路径

### 4.2 profile 组合

- `:smoke`
  - 用于开发 edit-run，包含最常用、覆盖面最大的能力子集
- `:core`
  - 用于 pre-merge，包含 `:smoke` + 高阶 AD 常见路径
- `:full`
  - 用于夜间/发布前，覆盖全部能力画像

## 5. 架构与目录建议

建议新增（或重构）目录：

- `src/models/precompile/registry.jl`
  - 定义能力枚举、profile 映射、统一调度 API
- `src/models/precompile/capability_gap_solver_ad.jl`
- `src/models/precompile/capability_thermo_derivatives_ad.jl`
- `src/models/precompile/capability_conserved_charge_highorder.jl`
- `src/models/precompile/capability_phase_cli_scan.jl`
- `src/models/precompile/capability_transport_workflow.jl`

统一公开 API：

- `run_precompile_capability(cap::Symbol; strict::Bool=false)`
- `run_precompile_profile(profile::Symbol=:smoke; strict::Bool=false)`
- `list_precompile_capabilities()`
- `list_precompile_profile(profile::Symbol)`

## 6. 关键实现要点

### 6.1 类型形状收敛（复用核心）

- 在能力实现中固定关键容器与维度（例如 `SVector{3,Float64}`、固定 chunk 配置）。
- 减少同语义不同参数形状引发的重复特化。

### 6.2 入口统一

- `scripts/dev/precompile_workload.jl` 仅调用 `run_precompile_profile(:full)`。
- `scripts/dev/build_sysimage.jl` 仅引用上述 workload 文件，不再内嵌场景逻辑。
- 测试 runner warmup（`TEST_PRECOMPILE_WARMUP`）调用 `run_precompile_profile(:smoke|:core)`。
- 扫描脚本 warmup 调用 `run_precompile_profile(:scan_equivalent)` 或能力子集。

### 6.3 容错策略

- 默认 `strict=false`：某能力 warmup 失败只告警不中断主流程。
- CI/门禁场景可切 `strict=true`，确保画像执行失败可显式暴露。

## 7. trace 增量回收机制

### 7.1 输入

- 代表命令集（最小集合）：
  - unit/integration/regression/validation smoke
  - phase CLI smoke
  - conserved charge scan 小网格

### 7.2 输出

- `trace_baseline.jl`（版本化基线）
- `trace_delta.jl`（新增签名）
- `trace_delta_focus.jl`（AD/solver 关键签名过滤）

### 7.3 回收规则

- 新增高频签名按“能力归属”回收，不按文件归属回收。
- 无法归属的签名进入“待归档池”，人工评估后并入新能力或忽略。

## 8. 治理与门禁

建议新增检查脚本：

- `scripts/dev/check_precompile_trace_budget.jl`
  - 指标1：关键命令 trace 行数不超过预算阈值
  - 指标2：focus 签名新增数不超过预算阈值
- `scripts/dev/check_precompile_profile_coverage.jl`
  - 指标：每个 profile 至少包含规定能力集合

CI 门禁建议：

- PR 级：仅做预算告警（不强阻断）
- nightly 级：超过阈值时阻断并要求补齐能力画像

## 9. 实施计划（分阶段）

### Phase 1（低风险，先收敛入口）

- 建立 `registry.jl` 与能力文件骨架
- 迁移现有 `run_precompile_workload` 到 `run_precompile_profile`
- runner/脚本改为统一入口

完成信号：

- 同一 profile 在测试与脚本中可重复调用
- 旧命令仍可运行

### Phase 2（中风险，提升复用率）

- 增加类型形状收敛
- 对 trace delta 热点签名做能力回收

完成信号：

- AD 关键流程冷启动耗时进一步下降
- trace delta 焦点签名数下降

### Phase 3（治理闭环）

- 增加 trace budget 与 profile coverage 检查脚本
- 接入 CI（先告警后门禁）

完成信号：

- 有稳定预算基线
- 回归可被自动发现

## 10. 风险与缓解

- 风险1：能力画像过粗导致漏覆盖
  - 缓解：trace 增量回收 + focus 清单定期补齐
- 风险2：画像过细导致维护成本高
  - 缓解：按“共享调用形状”而非“文件/功能点”划分
- 风险3：预编译覆盖上升但运行时无收益
  - 缓解：同时跟踪冷/热两轮指标，区分编译收益与数值收益

## 11. 验收标准

- A1：预编译入口已能力化，测试/脚本共用同一 registry API。
- A2：新增测试/脚本无需手工加“文件特化”即可获得已有能力画像收益。
- A3：关键 AD 流程冷启动相对当前再提升（目标区间 10%~20%，按场景分层统计）。
- A4：trace 增量回收与预算检查可运行并输出可读报告。

## 12. 下一步建议

- 先落地 Phase 1（入口统一 + registry 化），这是复用性的必要前提。
- 再执行 Phase 2（按 trace 焦点签名回收），以最小改动换取最大冷启动收益。
