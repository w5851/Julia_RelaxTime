# C++ 参考代码在 `usbar_to_usbar, mu_B=0, T=210/250 MeV` 上的运行与验证记录

**记录日期**: 2026-03-08  
**目标**: 复用 Fortran 同一套验证流程，对新加入的 C++ 参考实现做 `usbar_to_usbar, mu_B=0, T=210/250 MeV` 两个温度点的专项截面扫描，并与验证集、Fortran 结果交叉对比。  
**结论先行**: C++ 参考代码默认主程序可以运行，但默认输出不是验证集所需的单过程 `sigma(sqrt(s))` 曲线，因此需要补一个最小专项入口。补入口后，C++ 在 `T=250 MeV` 上与 Fortran 几乎重合，在 `T=210 MeV` 上除阈值附近新增一个更高的尖峰外，其余区段也与 Fortran 基本一致；相对文献验证集，两者仍然同方向偏大，因此当前偏差不是 Julia 独有问题。

## 1. 工程勘查与过程映射

### 1.1 默认主程序行为

- C++ 工程是 Visual Studio 方案工程，默认入口跑的是整张 `T-mu` 平面扫描。
- 默认输出包括 `solution.txt`、`rex_time.txt`、`coe_sigma.txt`、`sca_rate.txt` 等输运相关文件。
- 这条默认路径给的是平均散射率和输运系数，不直接给文献口径的单过程 `sigma(sqrt(s))` 曲线。

### 1.2 `usbar_to_usbar` 的正确过程码

- 通过阅读 `set_rex_time()` 及过程码注释，确认本工程里真正对应 `usbar_to_usbar` 的不是 `usb_code`，而是 `sub_code`。
- 也就是说，这份 C++ 代码里的命名与 Fortran 旧工程并不完全同构，若直接按变量名猜过程，容易拿错通道。

## 2. 为验证补的最小专项入口

### 2.1 本轮新增内容

- 增加了一个只服务于验证的最小专项入口。
- 该入口只做两组定点:
  - `mu_B = 0, T = 210 MeV`
  - `mu_B = 0, T = 250 MeV`
- 每个点只保留最小求解链路:
  1. `set_mut`
  2. `newt(PNJL_mut)` 求平衡态
  3. `set_phi_and_mass`
  4. `set_pse`
  5. `tint(s, sub_code)` 逐点扫描总截面

### 2.2 本轮输出文件

- `results/usbar_mu0_state_summary_cpp.dat`
- `results/usbar_mu0_cross_section_T210_T250_cpp.dat`

其中截面文件显式同时写出:

- `sigma_fm2`
- `sigma_mb = 10 * sigma_fm2`

这样可以避免再把内部单位和写盘单位混在一起。

## 3. 构建与运行过程中的环境问题

### 3.1 Visual Studio 构建链不可用

- 当前机器上没有完整的 VS C++ 工具链，直接走 `.vcxproj` 构建会报 `Microsoft.Cpp.Default.props` 缺失。
- 同时，本机也没有 oneAPI MKL 的头文件和库目录，因此原工程的 VS 工程配置在当前环境不能直接复现。

### 3.2 MinGW 替代构建所做的兼容处理

- 用本地 `g++` 走替代构建。
- 为缺失的 MKL 依赖补了一个最小兼容头，只覆盖当前工程实际用到的:
  - `mkl_calloc`
  - `mkl_free`
  - `cblas_dcopy`
- 将工程内部把 C++ 关键字 `throw` 宏化的写法改成自有宏名，避免污染 `omp.h`。

### 3.3 运行时 DLL 顺序问题

- 机器上同时存在 Julia 自带和 MinGW 自带的以下 DLL:
  - `libstdc++-6.dll`
  - `libgomp-1.dll`
  - `libgcc_s_seh-1.dll`
- 若直接运行 `g++` 产物，系统会优先捡到 Julia 目录里的同名 DLL，导致程序装载阶段报 `0xc0000139`。
- 实际可行的运行方式是先把 `D:\mingw64\bin` 放到 `PATH` 最前面，再启动专项程序。

### 4.2 C++ 曲线相对验证集的对比

对比数据源:

- 文献验证集: `tests/validation/data/relaxtime_sigma_literature_digitized_longtable_v1.csv`
- 过滤条件:
  - `process = usbar_to_usbar`
  - `muB_MeV = 0`
  - `T_MeV = 210` 或 `250`

对比方法:

- 在验证集每个 `sqrt(s)` 位置上，对 C++ 曲线的 `sigma_mb` 做线性插值。

#### `T = 210 MeV`

- 重叠点数: `N = 62`
- C++ 曲线范围: `[0.467122, 1.328916] GeV`
- 验证集范围: `[0.467625, 1.189321] GeV`
- 平均倍率: `1.6900`
- 中位倍率: `1.6168`
- `MAD = 4.7842 mb`
- `RMSE = 8.7837 mb`
- 峰位/峰高:
  - C++: `sqrt(s) = 0.467122 GeV`, `sigma = 69.147437 mb`
  - 验证集: `sqrt(s) = 0.467625 GeV`, `sigma = 25.627966 mb`

判断:

- `T = 210 MeV` 时，C++ 在阈值附近直接出现了一个非常高的首点尖峰。
- 这使得它相对文献的偏差比 Fortran 还要更大一些。
- 但去掉阈值附近前段后，C++ 与 Fortran 在主峰之后的大部分区段仍然是高度一致的。

#### `T = 250 MeV`

- 重叠点数: `N = 49`
- C++ 曲线范围: `[0.326923, 1.280349] GeV`
- 验证集范围: `[0.349000, 1.180043] GeV`
- 平均倍率: `1.4818`
- 中位倍率: `1.4857`
- `MAD = 1.1382 mb`
- `RMSE = 1.6894 mb`
- 峰位/峰高:
  - C++: `sqrt(s) = 0.575643 GeV`, `sigma = 9.701768 mb`
  - 验证集: `sqrt(s) = 0.582275 GeV`, `sigma = 5.131584 mb`

判断:

- `T = 250 MeV` 时，C++ 与 Fortran 一样，峰位已经比较接近，但峰高仍明显偏大。
- 这一结论与前一轮 Fortran 验证完全同向。

## 5. C++ 与 Fortran 的直接对比

### 5.1 状态点对比

- 两个温度点上的凝聚、Polyakov loop 和夸克质量都与 Fortran 基本一致。
- 因此 C++ 与 Fortran 的主要差异不在平衡态求解本身。

### 5.2 截面曲线对比

用 C++ 曲线对 Fortran 采样点做插值对比，得到:

#### `T = 210 MeV`

- 全 300 点平均倍率: `1.0141`
- 中位倍率: `0.9996`
- `RMSE = 3.2981 mb`
- 但最大绝对差达到 `56.9707 mb`

进一步观察可知，这个大偏差几乎全部来自阈值附近最前段的额外尖峰。若只看 `sqrt(s) >= 0.48 GeV` 区间，则:

- 平均倍率: `0.9986`
- 中位倍率: `0.9996`
- `RMSE = 0.2221 mb`

也就是说，除阈值首段外，C++ 与 Fortran 几乎重合。

#### `T = 250 MeV`

- 全 300 点平均倍率: `1.0037`
- 中位倍率: `0.9995`
- `RMSE = 0.0164 mb`
- 最大绝对差: `0.1044 mb`

这说明 `T = 250 MeV` 上 C++ 与 Fortran 可以视为数值等价。

## 6. 本轮结论

### 6.1 关于 C++ 工程能否按同流程跑通

- 可以，但当前机器上不能直接依赖原始 VS 工程环境。
- 在 MinGW 替代构建下，需要额外处理:
  - MKL 最小兼容层
  - `throw` 宏污染
  - DLL 搜索顺序

### 6.2 关于 C++ 结果是否支持前一轮判断

- 支持。
- `T = 250 MeV` 上，C++ 与 Fortran 几乎重合，且两者都比文献峰高更大。
- `T = 210 MeV` 上，C++ 与 Fortran 在主峰后区段同样基本重合，但 C++ 在阈值附近多出一个更高的首点尖峰；即便如此，二者相对文献仍然是同方向偏大。

### 6.3 对整体诊断链路的含义

- 这进一步说明当前 `usbar_to_usbar` 的异常不是 Julia 单独引入的。
- Fortran 与 C++ 两份旧参考实现已经在主要区段上彼此印证，并共同偏离文献验证集。
- 因而后续优先级应继续放在旧模型/旧公式口径本身，而不是先怀疑 Julia 基础实现框架。

## 7. 建议的下一步

- 优先检查 `T = 210 MeV` 阈值附近首点异常是否来自:
  - `s_min` 取值方式
  - 阈值上方 `1 + 1e-5` 的采样起点策略
  - `tint` 在极靠近阈值时的积分数值稳定性
- 若需要进一步做三方对账，可把 C++、Fortran、Julia 全部统一插值到同一组 `sqrt(s)` 网格后，再比较:
  - `B0` / 极化函数
  - 分布函数 blocking 因子
  - strange 通道耦合常数与质量输入
