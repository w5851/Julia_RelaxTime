# 求解器优化与脚本固化主计划

更新日期：2026-03-30

## 1. 背景与目标

- 将“连续性求解 + 多初解竞争 + 约束过滤 + 选优”固化为统一求解器行为。
- 将回归门禁主断言统一收敛到 `tests/regression/`，脚本仅保留便捷封装与报告导出角色。
- 在求解器稳定后，再推进“每专题一个扫描脚本，支持单点/连续扫描两种模式”的脚本收敛。
- 与既有“脚本分类清理 + 前端/CI 固化”工作对齐，避免重复改造与返工。

## 2. 统一口径

- 目标函数口径统一为 `pressure_max`。
- 物理等价说明：`P = -Omega`，故 `pressure_max` 等价于 `omega_min`。
- 选解规则：仅在“通过硬约束”的候选集合中比较 `pressure`；不满足约束的高压强候选不得进入最终结果。

## 3. 分治策略（双轨 + 单向依赖）

### 3.1 轨道 A：治理与接入轨（当前分支延续）

- 目标：完成脚本分类、稳定白名单、前端/CI 首批接入对象清单。
- 约束：不绑定旧/新求解器内部 seed 细节，仅绑定统一入口契约。

### 3.2 轨道 B：求解器与回归轨（新分支）

- 目标：多初解竞争、约束过滤、`pressure_max` 选解、回归门禁补强。
- 输出：统一求解契约（含失败码/失败原因字段）供脚本与前端复用。

### 3.3 汇合顺序

- 先合入轨道 B（求解器稳定）。
- 再在轨道 A 执行脚本收敛与前端/CI 接线。
- 禁止在求解器未稳定时提前做大规模脚本入口合并。

## 4. PR 序列（建议）

- PR-1（已在进行）：脚本治理与文档固化。
- PR-2（下一步）：求解器优化 + regression 门禁新增/改造。
- PR-3（PR-2 之后）：脚本 `mode=point|scan` 收敛 + CI/前端接线。

## 5. 提交策略与明确提交节点（新增）

> 目的：让“是否提交、何时提交、一次提交包含什么”由主计划统一裁决，避免临时决策造成提交边界漂移。

### 5.1 分支策略

- `PR-1`：`feat/run-script-governance-batch-a`（当前分支）。
- `PR-2`：新建内核分支（建议命名 `feat/solver-multiseed-constraint-selection`）。
- `PR-3`：在 `PR-2` 合入后新建接线分支（建议命名 `feat/script-point-scan-unification`）。

### 5.2 提交节点（必须满足才提交）

- C1（文档主计划节点）
  - 条件：主计划 + 子计划 + 两份既有 active 文档对接完成。
  - 本次范围：仅 `docs/dev/active/*.md` 计划文档。
- C2（求解器内核节点）
  - 条件：多初解竞争 + 约束过滤 + `pressure_max` 选优逻辑可运行，至少有 unit 证据。
  - 范围：`src/models/**` + 对应 `tests/unit/**`。
- C3（回归归位节点）
  - 条件：关键门禁断言已进入 `tests/regression/**`，反例回归可稳定复现。
  - 范围：`tests/regression/**` + 必要文档说明。
- C4（脚本收敛试点节点）
  - 条件：至少 1 个专题脚本完成 `mode=point|scan`，且 smoke/regression 证据齐全。
  - 范围：`scripts/**` + `docs/guides/scripts/**` + 必要测试。
- C5（前端/CI 接线节点）
  - 条件：前端与 CI 使用同一参数契约，运行证据可追溯。
  - 范围：`web/**`、`.github/workflows/**`、`docs/api/**`、相关测试与文档。

### 5.3 提交门禁（每个节点统一执行）

- 至少执行并记录与节点对应的最小验证命令。
- 提交内容必须单一职责：禁止在同一提交混入“内核算法 + 前端接线”。
- 提交说明需注明：本次对应节点（C1-C5）、上游依赖、验证证据。

### 5.4 当前“提交问题”的主计划裁决

- 现在处于 C1 节点：允许先提交计划文档，不等待 PR-2 代码完成。
- PR-2 与 PR-3 的提交时机分别由 C2/C3 与 C4/C5 条件触发，不再临场判断。

## 7. 全量迁移策略（补齐缺口）

### 7.1 迁移范围（已锁定）

- 目标范围：**全部 `run_*.jl` 脚本**。
- 执行顺序：先完成“专题单入口压缩（`mode=point|scan`）”，再把压缩后保留的全部 `run_*.jl` 切到优化后求解器。
- 回归门禁例外：`run_*_regression.jl` 不再保留在 `scripts/`，统一迁入 `tests/regression/` 维护。

### 7.2 波次策略（已锁定）

- 采用“按专题分波次”推进，而非一次性全量改造：
  - Wave-1：PNJL 专题压缩与迁移。
  - Wave-2：RelaxTime 专题压缩与迁移。
  - Wave-3：其余专题/治理专题（analysis/dev）压缩与迁移。

### 7.3 完成判据（每波次统一）

- 脚本侧：该波次专题的 `run_*.jl` 已压缩到“单专题单入口（`point|scan`）”。
- 求解器侧：该波次入口已接入多初解 + 约束过滤 + `pressure_max` 选优。
- 测试侧：
  - 单元与集成 smoke 通过；
  - `tests/regression/` 中对应专题门禁通过；
  - 存在“高压强但不满足约束”的反例回归。
- 文档侧：`docs/guides/scripts/README.md`、`docs/guides/scripts/run_script_catalog.md`、`classification_manifest.toml` 已回填。

### 7.4 兼容与下线策略（已锁定）

- 旧脚本策略：**压缩完成即删除**，不保留兼容壳层。
- 原因：避免双入口长期并存导致维护负担与治理偏移。
- 删除门槛：仅在对应波次“脚本/求解器/测试/文档”四类判据全部满足后执行。
