# 项目代码审查整改任务单

更新日期：2026-03-11

> 目的：基于 [2026-03-09_项目代码审查与改进建议](docs/dev/active/2026-03-09_项目代码审查与改进建议.md) 的静态审查结论，拆分形成一份可执行、可验收、可追踪的整改任务单。

---

## 1. 背景与目标

当前代码库的核心数值能力已经较完整，但存在明显的迁移期遗留问题，主要集中在：

- 失败语义不清晰，部分接口会吞错后继续返回结果；
- 已知正确性问题被注释测试绕开；
- 兼容层长期保留，导致内部接口与校验逻辑重复；
- 若干热路径仍有显式临时分配与潜在的求解策略开销；
- 错误类型和命名规范未完全统一。

本任务单目标：

- 先修正影响正确性和排障效率的问题；
- 再收敛接口与验证层，降低维护成本；
- 最后在有基准依据的前提下推进热路径优化与命名清理。

退场方案（PNJLModel.consts）：

1. 现状边界：`PNJLModel.consts` 当前主要被 `src/models/rpnjl/RPNJLModel.jl` 读取；`src/models/pnjl_physics/PNJLModel.jl` 自身核心计算已统一走 `params::PNJLParams`。

4. 阶段 D3：当 `RPNJLModel` 与其测试完成迁移后，删除 `PNJLModel(consts::NamedTuple)` 构造入口，再移除 `consts` 存储字段，只保留 `PNJLCore.as_namedtuple(params)` 这种按需导出能力。

### 4.4 P2：命名与迁移期遗留清理

#### 任务 I：清理迁移期命名与 shim 标识

- [x] 盘点 `_nt`、`consts`、`*_lookup` 这类具有迁移痕迹的命名。
- [x] 为过渡函数统一采用 `compat`、`shim`、`adapter` 等显式命名策略。
- [x] 明确 public API、compat API、internal helper 的命名边界。

验收标准：

- [x] 新读者能从命名直接区分公共接口与兼容层。
- [x] 不再新增无语义说明的过渡命名。

命名边界约定：

1. Public API：面向外部调用方的稳定入口，使用领域语义主名，不携带 `_nt`、`legacy`、`lookup` 等迁移痕迹；例如 `average_scattering_rate`、`relaxation_times`、`as_relaxtime_inputs`。
2. Compat API：仅为历史调用方保留的过渡入口，命名必须显式体现兼容语义，统一采用 `compat`、`legacy`、`adapter` 或“旧名别名 + 弃用/兼容测试”策略；这类入口不得再被新的主路径测试或运行时代码直接依赖。
3. Internal helper：模块私有实现统一使用职责导向命名，如 `*_core`、`*_value`、`*_state`，禁止继续引入 `_nt`、`*_lookup` 这类迁移期语义不明的名称。
4. 退场顺序：先将主路径调用和常规测试切到 public API，再把 compat 调用缩到单独兼容测试文件，最后才允许删导出或增加弃用告警。

## 7. 风险与回退方案

- [ ] 风险：P0 整改会影响上层调用方对失败返回的既有依赖。
  回退：先保留兼容返回层，但默认启用新合同并对旧行为加弃用提示。

- [ ] 风险：性能优化可能在数值精度或可读性上引入副作用。
  回退：所有优化必须绑定基准和一致性测试，不满足即回退到前一实现。

- [ ] 风险：兼容层清理可能扩大改动面。
  回退：优先做边界收口和命名隔离，延后彻底删除历史接口。
