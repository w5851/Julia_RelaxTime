# 架构决策记录 (Architecture Decision Records)

## 概述

本目录包含QCD模型库项目的架构决策记录（ADR）。ADR记录了重要的架构和设计决策，包括决策背景、考虑的选项、最终决定及其理由。

## 什么是ADR？

架构决策记录（Architecture Decision Record, ADR）是一种轻量级的文档格式，用于记录软件架构中的重要决策。每个ADR描述一个具体的决策，包括：

- **背景**：为什么需要做这个决策？
- **决策**：我们决定做什么？
- **后果**：这个决策的影响是什么？
- **备选方案**：我们考虑了哪些其他选项？

## 为什么使用ADR？

1. **知识保留**：记录决策的原因，避免未来重复讨论
2. **团队对齐**：帮助新成员理解架构选择
3. **决策追溯**：当需要重新评估时，了解当时的考虑
4. **透明度**：让所有人了解重要决策及其理由

## ADR命名规范

ADR文件使用以下命名格式：

```
NNNN-title-in-kebab-case.md
```

- `NNNN`：四位数字序号（0001, 0002, ...）
- `title-in-kebab-case`：简短的标题，使用小写和连字符

**示例**：
- `0001-use-multiple-dispatch-for-models.md`
- `0002-choose-toml-for-configuration.md`
- `0003-parameter-validation-strategy.md`

## ADR模板

创建新ADR时，使用以下模板：

```markdown
# ADR-NNNN: 决策标题

## 状态

[提议 | 已接受 | 已弃用 | 已替代]

如果已替代，链接到替代的ADR：被 [ADR-XXXX](XXXX-title.md) 替代

## 背景

描述需要做出决策的背景和问题。

- 当前情况是什么？
- 为什么需要改变？
- 有哪些约束条件？

## 决策

我们决定采用什么方案？

清晰、简洁地描述决策内容。

## 理由

为什么选择这个方案？

- 这个方案的优势是什么？
- 它如何解决背景中描述的问题？
- 为什么它比其他方案更好？

## 备选方案

我们考虑了哪些其他方案？

### 方案A：[方案名称]

**描述**：...

**优点**：
- ...

**缺点**：
- ...

**为什么不选择**：...

### 方案B：[方案名称]

...

## 后果

这个决策会带来什么影响？

**正面影响**：
- ...

**负面影响**：
- ...

**风险**：
- ...

**缓解措施**：
- ...

## 相关决策

- [ADR-XXXX](XXXX-title.md) - 相关决策的链接

## 参考资料

- 相关文档、讨论、外部资源的链接

---

**日期**：YYYY-MM-DD  
**作者**：[作者名称]  
**审查者**：[审查者名称]
```

## 创建新ADR的流程

1. **识别需要决策的问题**
   - 架构变更
   - 技术选型
   - 设计模式选择
   - 重要的实现策略

2. **创建ADR文件**
   ```bash
   # 找到下一个序号
   ls docs/decisions/*.md | wc -l
   
   # 创建新文件
   touch docs/decisions/NNNN-your-decision-title.md
   ```

3. **填写ADR内容**
   - 使用上面的模板
   - 清晰描述背景、决策、理由
   - 列出考虑的备选方案
   - 分析后果和影响

4. **团队审查**
   - 在团队会议或PR中讨论
   - 收集反馈和建议
   - 达成共识

5. **更新状态**
   - 初始状态：**提议**
   - 团队同意后：**已接受**
   - 如果决策被推翻：**已弃用**
   - 如果被新决策替代：**已替代**

6. **更新本README**
   - 在ADR列表中添加新条目
   - 保持列表按序号排序

## ADR状态说明

- **提议（Proposed）**：决策正在讨论中，尚未最终确定
- **已接受（Accepted）**：决策已被团队接受并实施
- **已弃用（Deprecated）**：决策不再适用，但保留记录
- **已替代（Superseded）**：决策被新的ADR替代

## 何时创建ADR？

**应该创建ADR的情况**：
- ✅ 选择核心技术栈或框架
- ✅ 定义系统架构模式
- ✅ 选择数据存储方案
- ✅ 定义API设计原则
- ✅ 选择测试策略
- ✅ 重要的性能优化决策
- ✅ 安全相关的设计决策

**不需要创建ADR的情况**：
- ❌ 日常的代码实现细节
- ❌ 临时的解决方案
- ❌ 显而易见的选择
- ❌ 纯粹的bug修复

## 最佳实践

1. **保持简洁**：ADR应该简短且聚焦，通常1-2页即可
2. **及时记录**：在做出决策时立即记录，不要事后补充
3. **客观描述**：使用事实和数据支持决策，避免主观臆断
4. **包含备选方案**：记录考虑过的其他选项，说明为什么不选择
5. **更新状态**：当决策被替代或弃用时，及时更新状态
6. **交叉引用**：链接到相关的ADR、文档和讨论
7. **不修改历史**：不要修改已接受的ADR内容，而是创建新的ADR替代
