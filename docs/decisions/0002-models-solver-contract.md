# ADR-0002: 采用 Models 求解接口契约（Problem-like + solve）

## 状态

已接受

## 背景

项目已形成 `Models` 统一入口与多重分派主线，但求解接口规范仍分散在 README、API 页面和治理脚本中，缺少单点权威契约，导致：

- 新增能力时容易出现“入口一致、语义不一致”；
- 调用方可能无意绑定具体数值后端；
- workflow 返回字段与可诊断信息缺少统一最低标准。

同时，团队存在“是否全面转向 SciML 风格”的讨论。仓库现状显示主链路稳定、迁移成本高，不宜进行全量重构。

## 决策

我们决定：

1. 在项目内正式采用 SciML-like 的语义约束：`Problem-like + solve`；
2. 保持现有 `Models` 主链路与数值后端实现，不做全面 SciML 重写；
3. 以文档化契约作为第一阶段落地：
   - 新增 `docs/architecture/models_solver_contract.md` 作为单点规范；
4. 后续如需与 SciML 生态互操作，优先采用 adapter 层，而非改写主计算链路。

## 理由

### 选择该方案的原因

- 风险可控：不触动成熟主链路，避免大规模回归。
- 语义统一：在不更换后端的情况下统一调用和返回约定。
- 面向未来：为可选 SciML 互操作保留清晰扩展点。
- 工程落地快：文档与门禁先行，增量治理成本低。

### 为什么不直接全面引入 SciML

- 当前核心问题是接口治理，不是后端能力不足。
- 现有 workflow 与兼容层较长，全面迁移会引入显著回归风险。
- 在无明确 ODE/PDE/adjoint 统一需求前，重构收益不足。

## 后果

### 正面影响

- 新增功能有明确接口与返回契约，协作成本下降。
- 后端替换与实验空间保留，不强绑某一实现。
- 文档、测试、门禁可围绕统一契约持续增强。

### 负面影响

- 短期内需要补齐部分文档与门禁细节。
- 历史调用路径在过渡期仍需维护兼容说明。

### 风险与缓解

- 风险：规范落地不一致，形成“文档规范”与“代码现实”偏差。
  - 缓解：逐步补充门禁脚本与 API 文档一致性检查。

## 备选方案

### 方案 A：保持现状，不新增契约

优点：零改动成本。

缺点：规范继续分散，新功能风格漂移风险持续。

未选择原因：无法支撑中长期协作与演进。

### 方案 B：全面迁移到 SciML 原生接口

优点：生态对齐度高。

缺点：迁移成本与回归风险高，且当前需求不充分。

未选择原因：阶段目标与风险收益不匹配。

## 实施计划

1. 发布并维护 `docs/architecture/models_solver_contract.md`。
2. 在新增入口开发流程中强制对照该契约。
3. 分阶段引入轻量门禁脚本，检查入口与契约一致性。
