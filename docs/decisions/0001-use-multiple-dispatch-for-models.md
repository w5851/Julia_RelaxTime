# ADR-0001: 使用多重分派实现模型多态

## 状态

已接受

## 背景

QCD模型库需要支持多种相关但不同的模型（PNJL、rPNJL、磁场PNJL等）。这些模型共享一些通用的概念和计算流程，但在具体实现上有显著差异：

- **PNJL模型**：各向同性，标准的Polyakov势
- **rPNJL模型**：包含八夸克排斥项，修改的Polyakov势（Vandermonde项）
- **磁场PNJL**：需要处理Landau能级，磁场依赖的色散关系

当前实现存在的问题：
1. 所有代码集中在单一的PNJL实现中
2. 添加新模型需要大量代码复制
3. 难以在不同模型之间切换
4. 测试和维护成本高

我们需要一个架构方案来：
- 支持多种模型的共存
- 最大化代码复用
- 保持类型安全和性能
- 易于扩展新模型

## 决策

我们决定使用**Julia的多重分派系统**结合**抽象类型层次结构**来实现模型多态。

具体方案：
1. 定义`AbstractQCDModel`作为所有模型的根抽象类型
2. 定义领域抽象类型（`AbstractIsotropicModel`、`AbstractAnisotropicModel`等）
3. 具体模型（如`PNJLModel`、`RPNJLModel`）继承相应的领域抽象类型
4. 使用多重分派为不同模型类型提供特化实现
5. 在`src/models/base/`中提供共享的数值工具

## 理由

### 为什么选择多重分派？

1. **Julia的核心优势**
   - 多重分派是Julia的核心特性，编译器高度优化
   - 类型特化的代码生成，性能接近手写特化代码
   - 避免了传统OOP的虚函数调用开销

2. **代码组织清晰**
   - 方法定义与类型定义分离
   - 易于添加新方法而不修改类型定义
   - 避免了深层继承层次的复杂性

3. **扩展性强**
   - 添加新模型只需定义新类型和实现必需方法
   - 不需要修改现有代码
   - 第三方可以轻松扩展新模型

4. **类型安全**
   - 编译时类型检查
   - 未实现必需方法会在调用时抛出`MethodError`
   - 类型推断帮助发现错误

5. **性能优越**
   - 编译器为每种具体类型生成优化代码
   - 无运行时类型检查开销
   - 内联和其他优化自动应用

### 与项目需求的契合

- **代码复用**：通过`src/models/base/`共享数值工具
- **类型安全**：抽象接口强制实现必需方法
- **性能**：多重分派的零开销抽象
- **可扩展性**：添加新模型无需修改核心代码

## 备选方案

### 方案A：传统OOP（抽象基类+虚函数）

**描述**：使用类似Python/C++的OOP模式，定义抽象基类，子类覆盖虚方法。

**优点**：
- 许多开发者熟悉这种模式
- 强制子类实现抽象方法
- 封装性好

**缺点**：
- Julia不原生支持虚函数，需要手动实现
- 性能开销（函数指针调用）
- 不符合Julia的设计哲学
- 难以实现多参数分派

**为什么不选择**：
- 与Julia的核心设计理念相悖
- 性能不如多重分派
- 实现复杂且不自然

### 方案B：Trait系统

**描述**：使用Holy Trait模式或类似的trait系统来标记模型能力。

**优点**：
- 更灵活的能力组合
- 避免继承层次
- 可以表达正交的特性

**缺点**：
- Julia的trait支持不如Rust等语言成熟
- 增加了概念复杂度
- 对于我们的用例过于复杂
- 学习曲线陡峭

**为什么不选择**：
- 对于当前需求过度设计
- 模型之间的关系是层次化的，不是正交的
- 增加了不必要的复杂性

### 方案C：函数式方法（高阶函数+闭包）

**描述**：使用高阶函数和闭包来参数化行为，而不是类型层次。

**优点**：
- 非常灵活
- 避免了类型定义
- 易于组合

**缺点**：
- 缺乏类型安全
- 难以发现缺失的实现
- 性能可能不如类型特化
- 代码组织不清晰

**为什么不选择**：
- 缺乏类型安全是严重问题
- 对于复杂模型，代码组织会变得混乱
- 不利于编译器优化

### 方案D：模块化设计（无多态）

**描述**：为每个模型创建独立的模块，不使用多态。

**优点**：
- 最简单直接
- 每个模型完全独立
- 无抽象开销

**缺点**：
- 大量代码重复
- 难以在模型之间切换
- 测试和维护成本高
- 无法编写通用的扫描器和工作流

**为什么不选择**：
- 代码重复违反DRY原则
- 不支持我们的扩展性需求
- 维护成本过高

## 后果

### 正面影响

1. **代码质量提升**
   - 清晰的抽象层次
   - 代码复用最大化
   - 易于测试和维护

2. **开发效率提高**
   - 添加新模型快速（只需实现必需方法）
   - 共享工具减少重复工作
   - 类型系统帮助发现错误

3. **性能优异**
   - 编译器优化充分
   - 无运行时开销
   - 类型稳定的代码

4. **用户体验改善**
   - 统一的API接口
   - 易于在模型之间切换
   - 工厂模式简化模型创建

### 负面影响

1. **学习曲线**
   - 团队成员需要理解多重分派
   - 需要学习Julia的类型系统
   - 与传统OOP思维不同

   **缓解措施**：
   - 提供详细的文档和示例
   - 代码审查中分享最佳实践
   - 团队培训和知识分享

2. **初期开发成本**
   - 需要设计抽象接口
   - 需要重构现有代码
   - 需要建立基础工具库

   **缓解措施**：
   - 渐进式重构，保持向后兼容
   - 提供兼容层
   - 分阶段实施

3. **调试复杂性**
   - 多重分派的调用链可能不直观
   - 需要理解方法解析规则

   **缓解措施**：
   - 使用`@which`等工具辅助调试
   - 清晰的命名和文档
   - 提供调试指南

### 风险

1. **性能回归风险**
   - 抽象可能引入性能开销

   **缓解措施**：
   - 性能基准测试
   - 使用`@inline`等优化提示
   - 持续监控性能

2. **接口设计风险**
   - 初期接口设计可能不完善

   **缓解措施**：
   - 迭代改进接口
   - 保持接口最小化
   - 版本化管理
